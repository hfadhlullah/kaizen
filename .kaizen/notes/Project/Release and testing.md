# Release and testing

## In plain words
How kaizen is tested and published: the test suite that runs on every change, the one command that releases a new version to npm, and the desktop app builds that follow.

## What it does
Tests are `bun test` (all `*.test.ts`, `cli/` and `bot/`), run in CI on Ubuntu, macOS and Windows (`.github/workflows/test.yml`). The package is `kaizen-agent` on npm (version 1.79.1 in this checkout); `bun run release [patch|minor|major] [summary]` (`cli/release.ts`) bumps the version — minor when a `feat` commit landed since the last tag, else patch — commits `Release x.y.z: <summary>`, publishes to npm (tests first), pushes, then GitHub Packages. `bunfig.toml` (and `bot/bunfig.toml`) preloads `test/tmp.ts`: each run points `TMPDIR`/`TMP`/`TEMP` at one `kz-test-*` folder and removes it in a preload `afterAll` (bun test never fires `exit` for a preload); the folder is named `kz-test-<pid>-*` and the next run removes any whose process is gone, so an aborted run leaves nothing for long, and tests that skip cleanup no longer fill tmpfs `/tmp`.

## Where it lives
- `package.json` — `test`, `build:web`, `format` / `format:check` (Prettier over the frontend TypeScript: `web/*.ts`, `web/board/`, `bot/web/app/`), `release`, `prepublishOnly` (tests), `postpublish` (`cli/release.sh`: tag + GitHub release, made as a draft that `desktop.yml` publishes once the installers are attached; a failed desktop build leaves it a draft, so the updater never meets a release without `latest*.yml`).
- `site/` — the static landing page: plain HTML, CSS and JS with GSAP vendored in `site/vendor/`. No build step, not in the npm package. Live at kaizen.sarahdigital.id on the Cloudflare Worker `kaizen-landing`: `bunx wrangler deploy --name kaizen-landing --assets site --compatibility-date <date>`. The Desktop section (`site/main.js`) reads `api.github.com/repos/hfadhlullah/kaizen/releases/latest` and links each `kaizen-desktop-*` asset directly; it stays hidden, and the nav Download pill points at Install, until that release has desktop files. Screenshots in `site/media/` come from a scratch board; never from a real one, whose phone view lists real device names.
- `desktop/` — the Electron desktop app (own `package.json`, not in the npm package): starts `kaizen web` on a free port with a bundled Bun and kaizen copy (a newer `~/kaizen` wins), stops it on close. `bun run dist` builds this OS's installers; `KAIZEN_DESKTOP_SMOKE=1 <app>` starts the board, prints ready and quits. `.github/workflows/desktop.yml` builds Linux (AppImage, deb, rpm, pacman; x64+arm64), macOS (dmg, zip; unsigned) and Windows (NSIS; SignPath when its vars are set), and attaches them to the `v*` tag's release; electron-updater reads the `latest*.yml` there. The window has no system title bar (`titleBarStyle: hidden`, macOS `hiddenInset`, `titleBarOverlay` where `windowButtons()` (`desktop/src/server.ts`) says so — Windows and Linux except Hyprland (`XDG_CURRENT_DESKTOP`/`HYPRLAND_INSTANCE_SIGNATURE`) — recoloured through the preload's `titleBar(dark)` → IPC `kz-titlebar`) and pinch zoom is off (`setVisualZoomLevelLimits(1, 1)`). After an app update, `upgradeInstalled()` in `desktop/src/main.ts` runs `kaizen upgrade` on `~/kaizen` in the background when `needsUpgrade()` (`desktop/src/server.ts`) says it is an npm install older than the bundle (never a git checkout or a missing one), once per app version (`userData/upgraded.json`), with `upgradeCmd()`'s env (`KAIZEN_HOME` = the installed copy, the bundle's and Electron's variables dropped), output to `~/.kaizen/upgrade.log`, and a notification. An `update-test` job (`desktop/scripts/update-test.ts`) proves 0.0.1 updates itself to 0.0.2 on Linux and Windows. The AppImage's app-menu entry (`desktop/src/appimage.ts`) is `Exec=env APPIMAGE_EXTRACT_AND_RUN=1 "<file>" %U`: from the FUSE mount, Electron children still alive at quit or poweroff fault on unread pages when the mount goes away and die with SIGBUS (issue #77; `journalctl` shows `tmp-.mount_kaizen….mount: Deactivated` just before each dump), so it runs extracted: about 0.3 s and 414 MB of `/tmp` per launch, removed on exit. A direct run of the AppImage starts itself again that way early in `desktop/src/main.ts` (skipped in smoke and update-test builds, and when `APPIMAGE_EXTRACT_AND_RUN` is already set, so it cannot loop); `TMPDIR` cannot move the extraction (the launch fails). See `docs/desktop.md`.
- `cli/publish-gh.sh` — same tarball as `@hfadhlullah/kaizen-agent` on GitHub Packages.
- `cli/build-web.ts` — bundles `web/notebook.js`, `web/term.js`, `web/board.js` and `bot/web/app.js`, committed; `cli/notes.test.ts` fails when one is older than its sources.
- `cli/release.ts` — the `release` script: bump, commit, publish, push. Its `git push origin HEAD` pushes the current branch, so from a worktree branch push `HEAD:main` yourself.
- `cli/ui-audit.ts` — `bun run audit:ui`, a dev tool (not a `kaizen` command, not in CI): starts a scratch board (the newest 40 runs copied from the project, worktree and session fields removed, its own `HOME`, a git repo with one commit, port 7459 or `--port`) and headless Chrome, opens every screen and open state (board, run workspace and its menus, dialogs, all 16 Settings pages, Notes, Video, the phone pages) in light and dark at 1400 and 400px, and measures with `getBoundingClientRect`: row centres, column left edges off by 1–4px, one component class at two heights, and the side-by-side top bars' first rows. It writes `report.md` (and with `--shots` a screenshot per state, flagged boxes outlined) to `$TMPDIR/ui-audit` or `--out`; `--only name,settings-*` narrows it. Exits 1 on any flag outside `cli/ui-audit.allow.json`. About three minutes. `cli/ui-audit.test.ts` runs its measuring code on a fixture page where Chrome is found.
- `cli/*.test.ts` — tests beside the code. `assets/` — README art and the hero capture.

- Bundles feed the [[Notebook]], the [[Web board]] and its terminal, and [[Kaizen bot]]'s page.

## Watch out
- npm serves a new version only after its automated review finishes — minutes after `bun publish` says success; a re-publish answers 409 (`.kaizen/memory.md`).
- Tests that touch install/uninstall must use scratch `HOME` and `KAIZEN_HOME` ([[CLI]]).
- To exercise the board without real state: copy `.kaizen/` to scratch, `kaizen web --port N --no-open` with a scratch `HOME`; stop it with `fuser -k N/tcp` (`.kaizen/memory.md`).
- `bun publish` prints success about a minute before the npm registry serves the new version: `npm view` and the version URL answer with the old one or 404 meanwhile. Recheck after a minute before calling a publish failed. From 1.11.0 (2026-10-01) npm runs an automated review on a new version (status `Validating` on the package page) and serves nothing until it finishes: `bun publish` reports success and postpublish tags and releases on GitHub, but npm serves the old version for many minutes; nothing to approve, wait; a re-publish answers `409 Cannot publish over previously staged version`.
- To run `cli/install.ts` as if on Windows from Linux, use a wrapper file that does `Object.defineProperty(process, "platform", { value: "win32" })` and then `await import(<install.ts>)`. `bun --preload` with the same line does not take effect for it. Run it with `env -i HOME=<scratch> PATH=<dir with only bun>` so no real git or home is reached.
- GitHub's release downloads answer 5xx now and then (v1.76.0's desktop and test runs all failed on one 504 window). `setup-bun` is retried once after a pause in both workflows, and `desktop/scripts/fetch-bun.ts` checks the status and retries, so an error page is never hashed as the zip (that showed as a false "checksum mismatch").

## Persistent Tasks (2026-11-08)

Persistent Tasks adds cli/tasks.test.ts, cli/task-results.test.ts, cli/web-tasks.test.ts and web/board/task-page.test.ts. Fixtures cover UUID/CAS/idempotence, draft transfer, safe queue boundaries, policy gates under auto/full/lite, recovery, accepted linked follow-ups, immutable bytes, copy/storage failures, artifact containment/ranges and typed viewers. Runtime verification uses a scratch HOME/project, configured stand-in agent and real browser inputs; it does not prove compliance by every external model. Human beginner observation remains separate from automated UI checks.
