# Settings

Part of [[Web board]].

## In plain words
The Settings page: choosing agents and models, turning skills on and off or repairing them, signing in to more than one AI account, the microphone, and the optional desktop-control and reverse-engineering tools.

## What it does
**Settings page.** Laid out after Orca's (run `2026-10-30-settings-orca-layout`, evidence from the `2026-10-29-orca-rea-report` extract): on desktop `body.setv` hides the rail and the panel header; `.snav` has Back to app, search and the groups from `web/board/settings-pages.ts` (`SETTINGS_NAV`, `placeOf(key)`; a test checks every key in `cli/settings.ts`, an unplaced key falls to General). Every page is in the DOM and one shows, chosen in `filter()`; `store.setPage` and `?page=` hold it (replaceState, so Back to app leaves in one step). The map is page-only: `group` in `cli/settings.ts` still decides scope and the TUI's headings. Short choices are joined `.bar` segments, long lists stay steppers. Phone starts on the page list (`.sset.pick`), with a Settings back row.

**Settings → Phone.** Has the Tailscale connect card (`#phset`, `phone-setup.ts`) and the WhatsApp Bridge card (`#waset`, `whatsapp-setup.ts`), which links WhatsApp Web and displays a QR code to scan. The bridge daemon `cli/whatsapp-bridge.ts` ships with kaizen (so install and upgrade carry it); `cli/whatsapp.ts` starts it with `~/.kaizen/whatsapp` as its working directory (login in `auth/`, `chats.json`, and `bridge.json`: the bridge's random 127.0.0.1 port and a per-run token, mode 0600). The Baileys and qrcode libraries (exact versions, `DEPS` in `whatsapp.ts`) are fetched with `bun add` into that folder on the first Link click, not into the package, which keeps zero runtime dependencies; the bridge resolves them from there. Sending prefers this bridge, then falls back to Hermes (`cli/hermes.ts`). `kaizen send --whatsapp <file> [--to <chat | self>] [--text ..]` (`cli()` in `whatsapp.ts`, dispatched from `install.ts`) is how an agent sends a file through it. The bridge listens on loopback TCP, not a Unix socket, so it is the same on Linux, macOS and Windows; every request needs the token (a web page that guesses the port gets 403). It starts with `windowsHide` and `detached`, so no console window opens, and with the same `bun` that runs kaizen (`bunBin()`). `cli/whatsapp.test.ts` runs the real bridge against stand-in libraries. A running daemon keeps its old code until it is restarted.

**Settings → Agents.** Laid out after Orca's (run `2026-10-31-settings-agents-page`). `web/board/settings-agents.ts` draws Default agent (chips, `agent.default`, scoped), Permissions and Installed above the ordinary rows, which `placeOf` groups as Workflow, Subagents and Running agents. Per-user preferences live in `~/.kaizen/agents.json` (0600, `cli/agent-prefs.ts`, `GET`/`POST /agent-prefs`, POST under `strict()`): enabled, permissions, command, arguments, environment. No file means launches are unchanged. `agentUsable()` in `cli/state.ts` gates every offered list and Auto; `launchRun` refuses a turned-off agent; turning off the global default moves it to Auto, and `POST /settings` refuses a turned-off default. Settings bypass goes through the Run form's `yolo` path, so the session record and card mark follow; agent terminals opened with `/shell` show "· bypass" in their title instead. Environment reaches an agent as `env K=V` argv (visible in the process list; not applied on Windows), never in the `cmd` returned to the page or the manual command, and the page only sees names. Command and arguments refuse shell characters because the manual command joins them unquoted. `agent.keep_awake` (off/auto/on, machine-wide, `cli/keep-awake.ts`): the board's poll holds `systemd-inhibit` or `caffeinate`, which watch the board's pid so a crash releases them; auto counts board-run agents only.

**Settings → Skills.** `cli/skills.ts` (run `2026-10-31-settings-skills-page`) scans `skills/*` and `skills/media/*` for `SKILL.md`, with optional `skill.json`. `GET`/`POST /skills`, POST under `strict()`. `setSkill` removes a global link only when it points into a kaizen clone's `skills/<rel>`; a real folder or foreign link stays. A core row with an agent not `installed` shows **Repair** in place of *Always on*: `POST /skills {id, repair:true}` runs `repairSkill`, which relinks from the clone the core `kaizen` link points at (`installedClone`), refuses with a `kaizen upgrade` hint when that clone lacks the skill, and replaces a real folder only with `replace:true` plus the one-time `/skills` token (the page asks first when a row is `other`). `~/.kaizen/skills-off.json` holds the off-list, which global installs honour through `skillsToLink` (project installs ignore it; core is always linked, by name); uninstall still uses `SKILLS`. `/kaizen-*` command files for off skills are not removed. Project-level installs are untouched.

**Desktop control** (run `2026-10-31-computer-use`). `skills/optional/kaizen-computer/` has `"off_by_default": true` in its `skill.json`: it is linked nowhere until the user turns it on, by any install, global or project (`skillsHeld`, the `held` argument of `skillsToLink`). `~/.kaizen/skills-on.json` is the on-list; `setSkill(..., on, confirm)` refuses the on-switch without `confirm`, which the server honours only with the one-time token that each `GET /skills` mints and the page sends back (a curl call without it gets `confirm required`; stops accidents, not a determined local process). `kaizen computer apps|windows|state|click|set-value|type` (`cli/computer.ts`) refuses every verb while the skill is off (the helper reads the on-list itself too, so running it by hand refuses), passes argv to `cli/computer-helper.py` with no shell, prints one JSON line, and gives each error code a `recovery`; output over 200 KB is refused. The helper is ours (AT-SPI through PyGObject): a node tree capped at 300 nodes, depth 8 and 200 characters of text; the app is matched against a password-manager blocklist by name only (a manager inside a browser is not caught; SKILL.md and the row say so) before any of its tree is read; a `password text` node reports no value and refuses `set-value` and `type`. Not included: screenshots, keyboard shortcuts, macOS, Windows, launching apps. On Wayland the row shows a note (no shortcuts or screenshots), and `GET /skills` adds the helper's `check` result as the row's requirements. An app that does not expose a tree (some Electron apps) appears empty. GTK4 apps name themselves from the program name (`python3` for a bare script).

**REA** (run `2026-11-06-rea-skill-toggle`). Not a skill folder: `cli/rea.ts` builds one extra row that `GET /skills` appends (`reaRow`, id `rea`). The row reads agent configs only (`reaRegistered`: a pinned `rea-agents@x.y.z`, else just the server key — JSON `"rea": {` or TOML `[mcp_servers.rea]`, a global `rea` install, version unknown — in `~/.claude.json`, `~/.codex/config.toml`, `~/.gemini/settings.json`, …) plus `~/.kaizen/rea.json` (kaizen's switch); off and never set up, it runs nothing. On, it starts `npm view rea-agents version` (cached 1 h) and `npx -y rea-agents@<installed> doctor --json` (cached 10 min) without awaiting them, so the first look says "checking what it needs…". `POST /rea` under `strict()`: `{step:"plan", update?}` runs `setup --client <installed agents' REA ids> --dry-run --json` at the newest version and returns a one-time token bound to that version and client list (`reaPending`); `{step:"apply", confirm:true, token}` applies exactly that plan (`setup … --yes --json`) and saves `rea.json`; any apply attempt spends the plan. `{step:"off"}` runs REA's `uninstall --json` whoever set REA up, then names any registration left (Claude local/profile: `claude mcp remove --scope user rea`). Kaizen writes no agent config. The page (`web/board/settings-skills.ts` `reaSwitch`) shows the plan's files in a `confirm()` and an *Update to <v>* button when newer.

**Settings → AI Provider Accounts.** `cli/accounts.ts` (run `2026-10-31-provider-accounts`): `~/.kaizen/accounts.json` (0600) and a 0700 folder per account, which the tool fills; kaizen stores no token. `resolveAccount` takes a pick, "" for the normal login, or the tool's default, and returns an error rather than falling back. `launchRun` resolves pick, then the run's latest session record (`account`; a run started on the normal login stays there), then the default, and sets `CLAUDE_CONFIG_DIR` or `CODEX_HOME` on the launch and briefly in `process.env` around `sessionLaunch`, whose lookups read it. `/shell` and Claude resume follow too. Other headless calls (commit message, gather, chat) stay on the normal login. Usage per account reads `.credentials.json` server-side, so on macOS, where Claude uses the Keychain, it may show nothing; 401 means sign in again. The footer `/usage` is unchanged.

**Voice.** `kz-mic` in localStorage holds the microphone (`web/board/settings-voice.ts`); an unplugged one falls back to the default with a notice. Ctrl+Alt+D (a capture listener in `dictation.ts`, run `2026-10-31-orchestration-voice`) runs `mic()` on a stand-in field that pastes each chunk into xterm's hidden textarea. It works only while the page has focus.

**Models.** `agent.model.<tool>` (Settings → Agents → Models, installed tools only) feeds `agentConfig`, ahead of a hand-written `agent.<tool>` block; Claude has a row too (the main session) beside `subagents.model` and the per-stage `subagents.planner|builder|reviewer` rows. `agent.handoff_model.<tool>` rows sit in Agents → Handoff session (`web/board/settings-pages.ts`).

## Watch out
- Settings controls (`ctl()` in `web/board/settings.ts`): a switch for on/off, a `.bar` segment per value for the preset and numbers, and a `.step` stepper (`‹ value ›`, ids `<id>-prev`/`<id>-next`) for every other choice, Theme included. `stepper()` keeps the position and wraps at the ends: the shown value changes on each click, a config row saves 300 ms after the last click (one POST per burst), Theme applies at once. ←/→ press the arrows, the group is named by its row's `<label id="<id>-l">`, and the re-render puts focus back on the arrow pressed (`refocus()`).

- Settings scope (`Settings for` select, below the search): All projects edits `~/.kaizen/config.yml`, a project edits its own `.kaizen/config.yml` (created empty, not as a defaults copy). Opens on the board's project (`store.setScope`, All when the board shows all); changing it never moves the board. `GET /settings?scope=<state dir>|all`, `POST /settings {key, value, scope}` or `{key, scope, reset: true}` (`resetSetting` removes the key and only the comment lines the defaults carry for it); no scope keeps the cwd resolution. Rows carry `own` (project scope: Reset link). All projects shows the global value only; it no longer lists projects that set a key otherwise. Board-group rows are always global. Without a scope, `listSettings`/`setSetting` still resolve from the cwd (TUI). The What's new popup (`.updpop`) anchors to the update bar, not its button, so it stays on a phone screen.

- A settings row whose `idle` reason is set (from `when` in `cli/settings.ts`) gets `.srow.off`: dimmed, still clickable, reason appended to its hint.

- Settings and the Icebox share one panel and fill it after a fetch: `openSettings()` / `openSources()` must keep the `store.pageGen` check (`go()` bumps it), or a slow answer paints one page under the other's title. Switching to one of them clears the body to a Loading line before the fetch, or the old page shows under the new title until it answers.

- Since 2026-10-14-board-sidebar, Settings and Sources are the run panel docked as a page (`go(view)` in `web/board.html`, `body.paged`, `aside.docked`, `?view=`): `close()` is a no-op while `view!=="board"` and `open()` returns to the board first. Any new way of opening a card must go through `open()`, or the run renders inside the Settings page. The side menu block (CSS, markup, inline script with the global `setTheme`) is held equal on `board.html` and `notes.html` by a test: edit both.

- A regex that skips a block with `(?:[ \t]+.*\n)*?` backtracks for seconds on a long commented config when the key is absent (`agentConfig`); write it `(?:[ \t][^\n]*\n)*?`. `agentChoices` runs it once per installed agent, so on a slow pattern every `/onboarding` read stalled the whole board.

## Agent launch and phone keyboard (2026-11-08)

New agent launches expose a per-launch bypass permissions switch: in the phone's New sheet, and at the top of the agent list in the workspace +/split menus (`run-view.ts`; no separate dialog). It starts from the saved default (the default agent's) and resets each time the menu opens; only a flipped switch sends `yolo`, so an untouched one leaves each agent's own saved setting in force. Unsupported agents and account sign-in never receive bypass flags. Settings defaults are unchanged.

## Explore workflow option (2026-11-08)

Settings → Agents → Workflow has `explore.enabled` (false by default), a project/global switch independent of the installed core skill. `cli/config-values.ts` supplies scalar lookup shared by Settings and the launch defaults without a state/settings import cycle. `/agents` returns the resolved Explore default; the Run form can override it for one launch.

## Research key (2026-11-09)

Settings → Integrations → Research holds the Firecrawl key for `kaizen search` / `kaizen scrape`: a password field with Save, then Test (one search credit) and Remove. `GET /research-key` answers `{set, source, hint}` only, the last four characters, never the key; with `FIRECRAWL_API_KEY` in the board's environment the field is disabled and that key wins. Per user, so no scope.
## ChatGPT rows (2026-11-09-icebox-ai)
`sources.model` / `sources.effort` are "ChatGPT model/effort for the icebox" (gathering social posts, sorting captures, drafting tasks) and no longer carry a `when`, so they are never shown idle.
## Normal login on AI Provider Accounts (2026-11-09-accounts-normal-login)
`GET /accounts` also returns `normal` (one per installed tool: `signedIn`, `who`, `plan`, `via`, `usage`, `isDefault` when no account is the default) and `who`/`plan`/`via` on each account. They come from `loginStatus()` in `cli/accounts.ts`: `claude auth status --json` / `codex login status`, with `CLAUDE_CONFIG_DIR` / `CODEX_HOME` for an account and unset for the normal login, raced against a 5 s timeout (a killed CLI's children can hold its pipes open), cached a minute (`acctLogin`, cleared on any account change), falling back to the old file-exists check without the CLI. Codex's "an API key - sk-…" keeps only the method. The page draws a "Your login" row first per tool (`normalRow` in `web/board/settings-accounts.ts`); its Default posts `id: ""`, and its Sign in posts `/shell` with `account: ""` and `login: true`, which signs in the normal login rather than the default account.
## Persistent Tasks (2026-11-08)
Tasks uses configured workflow agent/account/model/permissions. The task-specific initial proposal gate is persisted on its run and does not alter saved Settings or enable bypass. Unavailable configured agents leave a recoverable saved task.

- Optional skill `lemo-opuscar` (`skills/optional/lemo-opuscar/`): film styles, off by default like `kaizen-computer`. Only the small wrapper ships (MIT licence included); on first use its `scripts/setup.sh` clones the style library into `~/lemo-opuscar`. Settings → Skills asks first (`WARN` in `web/board/settings-skills.ts`); `kaizen-video` hands named-art-style films to it when it is on.
