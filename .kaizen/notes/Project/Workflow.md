# Workflow

## What it does
The product itself: a staged workflow (plan, approval, build, independent review, bounded fix loop) that an agent follows from markdown instructions. Nothing here is code; the agent reads it and does the stages. How a run goes for a user is in `docs/guide.md` ("How a run goes"); the full behaviour is in `skills/kaizen/SKILL.md`. The guide also covers Video page sends: large MP4s go to WhatsApp as documents.

## Where it lives
- Orchestration (optional, `skills/kaizen/spec-plan.md`, `spec-build.md`, `spec-review.md`, `spec-main.md`): a plan may carry a `## Workers` split approved with `workers: approved` in `02-approval.md`; the build agent coordinates, the review reads `workers.json`. Off by default and ignored in lite.
- `skills/kaizen/SKILL.md` — entry point: commands, modes, runner, state layout. Under `runner: lite`, `review.executor` (`inline` default, `subagent`, `ask`) decides whether the review still goes to a cold `kaizen-reviewer`; the `low` preset sets `inline`.
- Review findings at every severity enter the bounded fix loop by default, including short lite runs; the reviewer says `PASS` only with zero findings. The backlog records only what the user asked to backlog in their own words: open findings, unverified checks and out-of-scope tasks are offered by number at the approval and filed only when named, and in `auto` mode nothing is filed.
- `skills/kaizen/spec.md` + `spec-plan.md` / `spec-build.md` / `spec-review.md` / `spec-main.md` — the stage contracts; each reader takes core plus its own stage.
- `skills/kaizen/gather.md`, `discover.md`, `docs.md`, `status.md`, `settings.md`, `install.md` — one file per sub-command.
- `skills/kaizen/config.default.yml` — every setting and its default. Only keys something reads belong there; the review checks, track and backlog paths are fixed in the spec files, not settings.
- `cli/handoff.ts` — on a worktree run from a board terminal, `kaizen handoff start` asks the board for a second agent in the worktree; it ends with `kaizen handoff done|blocked`, and the board wakes the first agent, which reports and takes the final approval. State is `runs/<id>/handoff.json`; exit 3 means build here. A run cut from a non-default local branch records `base_branch` and lands by local merge. A side run (requested while another run is in flight, `SKILL.md` *Follow-ups are runs too*) uses `kaizen worktree start <id> --default`: off the remote default branch, never adopted into the folder it is run from, no `base_branch`; handoff applies under `lite` too, and the first agent returns to its own run.
- `cli/worktree.ts` — each run builds on branch `kaizen/<id>` in `.kaizen/wt/<id>` (`git.worktree_per_run`); a run set up by hand (a roadmap on one feature branch) records its real branch in `state.json` `branch`, and `branchFor(project, id)` returns that when it is a safe branch name, else `kaizen/<id>`: the Git tab, push, PR, merge, land and cleanup all go through it, never the base it lands on (remote default, feature base, HEAD). Land and cleanup keep the worktree and branch while another run's `state.json` still records the same worktree or branch (`sharer`), and cleanup says which run. Workers read the run's branch through `branchFor` too; creating a worktree and worker branches still use `branchOf`; `kaizen worktree start|land <id>` makes and lands it, and `state.json` records `worktree` and `branch`. Run notes stay in the project's `.kaizen/runs/`. It also lists a project's workspaces (`workspaces()`), places a run in one (`wsOf()`) and adds a branch worktree for the board (`addWorktree()`): see [[Web board]].
- `skills/kaizen/adapters.md` — running it under Codex or Antigravity.
- `agents/kaizen-*.md` — the planner, builder and reviewer subagents.
- Stage subagent models (Claude Code): `subagents.<stage>` (`planner`, `builder`, `reviewer`; the builder also runs fix rounds, the reviewer rechecks), else `subagents.model`. The main agent reads it with `kaizen model <stage>` (`subagentModel` in `cli/state.ts`) and passes it on the Agent call. `launchRun` and `agentLine` (`cli/workers.ts`, so the handoff agent and workers too) add `subagentEnv`: `CLAUDE_CODE_SUBAGENT_MODEL` / `CLAUDE_CODE_SUBAGENT_EFFORT` from `subagents.model` / `.effort`, the defaults Claude Code falls back to when the call names no model. The handoff agent's own model is `agent.handoff_model.<run's tool>` (`handoffModel` in `cli/workers.ts`, passed by `tendOne` in `cli/web.ts` as `agentLine`'s pick), else the run's model.
- `commands/kaizen-*.md` — Claude Code slash commands, each a one-line hand-off to the skill.
- Roadmaps: a project too big for one run, of any kind, gets `.kaizen/roadmaps/<name>.md` (phases, status, decisions) on top of child cards. `cli/roadmap.ts` reads it; `skills/kaizen/roadmap.md` holds `/kaizen roadmap`, `next` and `run`. One run stays the default.
- `skills/kaizen-concept/SKILL.md` — `/kaizen concept`: product type first (its table sets what concepts differ on and what gets prototyped), then market and the users' medium; concepts differ by promise, image medium, type and signature mechanic; a craft pass; UX and platform rules with a 30-item checklist in `skills/kaizen-concept/ux-rules.md` (sourced: HIG, Material, Fluent, WCAG, NN/g), a frame per platform (phone, browser window, desktop window, landing page); a word budget of about 10 words of prose per app screen; sample labels and screen jumpers outside the app; the review page as a menu of concept tiles with a detail view per concept (preview, votes and comments by name); the approved concept ends in an extracted `DESIGN.md`, tokens and a handoff note.
- `skills/kaizen-help/` — the help card; `skills/media/` — `kaizen-deck/`, `kaizen-video/` (footage editing and from-scratch films on HyperFrames; any preset works for either start, `make_tiktok.py`/`make_film.py` bridge to the other engine; a style.json with `"engine": "canvas"` builds with `canvas.html`, a camera over one large canvas, see `references/canvas.md`; a template preset (`preset.json`, e.g. `app-promo`) films the user's product with `record.mjs` and builds with `make_promo.py`, see `references/promo.md`; presets with a `.hidden` file stay off the New video wizard): separate skills shipped in the same package.
- `docs/guide.md` documents the board's Source control tab and the first-run welcome; `cli/worktree.ts` supplies that tab's branch and pull request state ([[CLI]]).

## How it connects
- Global knowledge: the reviewer saves lessons that hold beyond the project with `kaizen remember` and lists them in `04-review.md` `## Remembered`, which the final report repeats, and only past a four-test gate in `spec-review.md` (reusable, high-signal, evidenced, new — recall before saving; zero is normal); the planner runs `kaizen recall` and ends its Framing with `Recalled:` (`spec-review.md`, `spec-plan.md`, `spec-main.md`). See [[CLI]].
- A request for a whole app (more than one module) is planned as a roadmap (`spec-plan.md`, *A whole application is a roadmap*): `## Discovery` (up to three question rounds), `## Foundation` (frontend, backend and their contract, database and data model, auth, hosting and deploy as chosen in discovery (CI/CD, Docker, managed platform, mobile store builds), layout, and the look and feel asked in discovery) and a numbered `## Roadmap` of end-to-end feature increments, ending with a go-live increment for an app real people use. The run builds increment 1, the skeleton; at approval the main thread files increments 2..N with `kaizen card add --parent` (`spec-main.md`, *Child cards*), and the parent card lists them as children. An increment run reads its parent's Discovery and Foundation as binding.
- A child card is filed as `kaizen card add "<short title>" --notes "<details>"`: the title stays a few words, the details land in the task's notes under `Parent:` (`addCard` in `cli/state.ts`).
- Any run whose request names an existing thing without its source (app, APK, binary, file format, device, protocol) offers REA once (`spec-plan.md`, *Offer REA*); when REA is not connected it offers to install it (`rea-agents doctor`, a `setup --dry-run` shown to the user, `setup --yes` only on approval, then a restart and resume), give the command, or skip; the main thread asks discovery rounds and that question (`spec-main.md`, *Discovery rounds*).
- Runs are written to `.kaizen/runs/<id>/`; [[Web board]] and [[Terminal board]] read them through `cli/state.ts`.
- [[CLI]] installs these folders as links into `~/.claude/`.
- `/kaizen docs` writes this vault. During a run the builder updates the notes whose `sources` it changed, and the *Docs gate* in `spec-main.md` makes the main thread finish the job before the final report and before `stage: "done"`, in every runner and mode: fix-iteration changes, and changed files no note covers (added to a note's `sources`, or a new note). The gate runs `kaizen docs lint` after those updates; see [[CLI]].

## Watch out
- Never write `model:` or `effort:` into `agents/kaizen-*.md`: the installed files are links shared by every project, and a frontmatter line beats the env defaults. An older SKILL.md did write `effort:`, which turned the links into copies; the installer (`linkState` in `cli/install.ts`) relinks a copy that differs only by that line.
- `skills/kaizen/` is the source; `.kaizen/spec*.md` in a project are copies (`kaizen --check` reports drift). In this repo the copies are not committed (`.gitignore`).
- Roadmap mode is for more than one module; a single screen or feature stays one run, and outside roadmap mode the foundation questions stay one round.
- `stage` must be one of `plan`, `build`, `review`, `done`, `abandoned` — `columnOf()` in `cli/state.ts`; any other word shows as planning (`.kaizen/memory.md`).
- Global skill links on this machine point at `~/kaizen`, a separate clone: a skill change is live elsewhere only once `~/kaizen` has it (`.kaizen/memory.md`).
- Final-approval gate (`gateOf` in `cli/state.ts`): with `approvals.review` on, a run id from 2026-10-29 on (`GATE_FROM`) whose `03-impl.md`/fix reports name existing files in backticks under a heading with "chang" or "files" (`changedPaths`; whole report when none) is accepted only by a line `accepted: <ISO> by user via board|chat` or `accepted: <ISO> auto (auto_accept)` in `02-approval.md` (`acceptance`, `recordAcceptance`). The board's `/decide` approve-as-is at review and `POST /accept` write it; the main thread writes the chat line. Without it a done run is "done, not approved" and `commitPush` refuses. `auto_accept` (top-level, default false) lets `auto` runs write the auto line. The rule text is in `spec-main.md` *Final approval*. `reviewGateOn` ignores comments, CRLF and quotes; `boardCards` caches the gate per run by the mtimes of the files it reads. The `approvals.review` setting row shows in every mode. Agents can still write `stage: done`, but `readRuns` reports a gate-`needs` done run as `review` / `approvals.review` (via the cached `accepted()`), and `healRuns` (called from `/state` and the terminal board, never from `readRuns`) rewrites its state.json that way (atomic, skipped if the file changed; checks `"stage": "done"` cheaply before parsing) and sets `healed: true`, which `readRuns` and the card carry (`finishRun` clears it). A healed card's panel (`web/board/panel.ts`) shows only Approve, which posts `/accept` (acceptance line + `finishRun`, no agent launch; `/accept` refuses a genuine review), and no findings/Fix form; Commit & push stays for the finished run. Genuine reviews keep `/decide`. `finishRun` / `kaizen done <id> [--user-approved]` is the sanctioned finish: refused while the gate says `needs`, the flag records the `via chat` line first. The card's `accept: needs` now only appears if the file still says done, so the board's Approve for a healed run is the normal review Approve (`/decide`, which records the line and resumes the agent to run `kaizen done`). Runs before `GATE_FROM` (e.g. all of Zen-Landing) stay done.
- Agents set `stage`, `awaiting` and `iteration` with `kaizen state <id> key=value` (spec.md, Stage 0); `done` still goes through `kaizen done`. The stored `track` word is the nearest standard one (`code`, `writing`, …), mapped again by `trackOf()` in `cli/knowledge.ts`, while the free description lives in `00-request.md`.
- Every gate item in a plan ends with `— proof: <how>`; the builder also answers the request's own requirements as `R PASS`/`R FAIL` lines before handing over (spec-plan.md item 6, spec-build.md gate block).
- Area lessons go in each area note's `## Watch out`, not `.kaizen/memory.md` (spec-review.md); memory.md keeps cross-project lessons.
- `auto_guard` (`max_files`, `stop_on`) stops an auto run at the final approval (spec-main.md *Auto guard*); planners run `kaizen related` on their manifest and add `Related:` to the Framing (spec-plan.md). Stage times exist only for runs with a `stages.log`: file mtimes move when `02-approval.md` gets its accepted line.

## Landing
A land rebases first, resolves only `git.generated` paths, runs `git.land_check` after pulled commits, and records a failure in `runs/<id>/land.json`. The board reads it as the card's `land` and each agent's `land`, showing `Conflict` or `Land failed` with a red `!`.
